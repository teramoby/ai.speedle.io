Speedle MCP · Coming soon

Speedle MCP: one package, two deliberately separate modes

@speedle/mcp is planned as one npm package with a speedle-mcp binary that runs as a local stdio MCP server. It is not published on npm yet.

Follow the repository
Mode 01 · Launch previewcheck

Authorization checks

The planned check mode registers only the authorization-check tools and reads only ADS configuration. It answers authorization questions; it does not enforce anything in the calling application.

  • Read-only authorization checks through the Speedle ADS REST API.
  • Subject, resource, action, and typed attributes as inputs.
  • ADS base URL, service name, and optional bearer token from environment variables.
Read the check-mode issue
Mode 02 · Launch previewmanage

Policy design and management

The planned manage mode registers only the management tools and reads only PMS configuration for designing and managing Speedle policies through the PMS REST API.

  • Services, authorization policies, and role policies.
  • SPDL validation and effective-policy explanation helpers.
  • A read-only option; destructive deletes require explicit target confirmation.
Read the manage-mode issue

Keep policy management out of the governed agent

Never give manage to an agent that is itself governed by these policies. An agent holding both check and management tools could be prompted into granting itself access.

There is no default mode that exposes both. Running with no mode is planned to print usage and exit non-zero.

Speedle policy modeler · Open source skill

Turn policy documents into reviewable SPDL

An Agent Skill for Claude Code that reads an employee handbook or regulation, asks about what the document leaves open, and models the result as RBAC + ABAC policies. It never guesses a rule.

What it produces5 files

From handbook clauses to tested policies

Every policy cites the clause it implements, or a confirmed answer. The model document includes a Mermaid role-inheritance diagram and each policy's rationale.

  • Importable .spdl for the file store, checked with spctl check.
  • ABAC conditions for department, location, data class and amount.
  • Executable cases covering allows, denies and approval boundaries.

AI-based risk detection · Being built

AI risk detection looks wider. Policy keeps the veto

AI can look across more dimensions and relationships to find risk that a single rule does not see. Deterministic policy still makes the decision and holds the veto: AI never grants what policy denies.

Deterministic foundation

Policy-based access control

Policy evaluates a defined request and returns a precise, explainable decision. It holds the veto: when policy denies, the answer is deny.

  • Explicit rules for subjects, resources and actions.
  • Deterministic outcomes that can be explained.
  • A policy denial that no AI risk signal can overturn.

DENYPolicy denial is final.

Approach being built

AI-based risk detection

This is a direction Speedle is exploring and building, not a shipped feature. The approach examines risk across more dimensions and relationships—such as unusual combinations of agent, user, data and task context.

  • Looks beyond a single request attribute.
  • Examines relationships across the wider context.
  • Adds a further layer of protection on top of policy.

It never grants access that policy denies.

02

Access management for AI

Govern access while you build and run AI

Speedle’s policy engine applied wherever AI systems touch data, models, tools and other agents: in Build, before a model serves, and in Run, while it serves and acts. These are solution patterns, not shipped integrations with any ML or agent platform.

Concept

One decision point for building and running AI

Each area has an enforcement point in your application. It asks Speedle before it acts and enforces the answer. Identity comes in from your IdP; decisions and their explanations go out to your audit trail.

Each SPDL example below was parsed and evaluated with the Speedle file store against allow and deny cases. Names, paths and attributes are illustrative; your application supplies the attributes when it asks for a decision.

Build

Before a model serves: data, training and release

01 / Data & training

Which pipelines may train on which data?

Training jobs read datasets, use compute and write checkpoints. The application asks before each dataset read, job start and checkpoint export, passing sensitivity, tenant, consent and region as attributes.

Subjects
Training pipelines as entities; ML engineers and their teams.
Resources and actions
Datasets: read. Training jobs: start. Checkpoints: export.
Enforcement point
The data loader before it opens a dataset, the job scheduler before it allocates compute, and the artifact store before an export.

02 / Model release

Who may release a model?

Registering, approving, promoting and rolling back models are separate actions with separate owners. Separation of duties keeps the person who trained a model from approving it.

Subjects
ML engineers, release managers and the service identities of release pipelines.
Resources and actions
Models and endpoints: register, approve, promote, rollback.
Enforcement point
The model registry and the release pipeline, before each change of model or endpoint state.

Run

While AI serves and acts: retrieval, agents, tools and other agents

03 / Inference & RAG

Only what the user may read enters the prompt

Users, apps and tenants call models. For permission-aware RAG (retrieval-augmented generation), the retriever asks Speedle about each document or collection before its content enters the prompt, so the model only sees what the person behind the request may read.

  1. 1The retriever finds candidate documents.
  2. 2It asks Speedle per document or collection, with the user’s tenant and clearances.
  3. 3Only allowed content goes into the prompt.
Subjects
The user behind the request, with their groups; client applications and tenants as entities.
Resources and actions
Collections and documents: retrieve. Models: invoke.
Enforcement point
The retriever before a document enters the prompt, and the API gateway or inference service before it routes a request.

04 / Agents acting for users

What may an AI agent do on behalf of a user?

The agent has its own identity. On behalf of a user, the request carries both the user and the agent as principals, and every grant names both roles, so the agent gets only what both may do. Scope is bound to the task and its expiry, and high-risk actions need a human approval.

Subjects
The agent as an entity plus the delegating user. The agent alone, or the user without the agent, matches no grant here.
Resources and actions
Tickets: read, update. Orders: refund, a high-risk action.
Enforcement point
The agent runtime or the application backend, before the action reaches the business system. The approval step records a human approval and the application passes it as approved_amount.

05 / Tool calls (MCP)

May this AI agent call this MCP tool, with these arguments?

Every tool call is checked before it runs. The tool is the resource, the call is the action, and the arguments become attributes, so limits such as a refund amount are part of the policy.

Subjects
Agents, each with its own entity identity and role, so privileges stay per agent and per tool.
Resources and actions
Tools: call, with the tool arguments as attributes.
Enforcement point
The MCP client host, or a gateway in front of MCP servers, before the tool executes.

06 / Agent-to-agent (A2A)

Which agent may call which agent for A2A authorization?

Each hop in a delegation chain is checked. The callee may receive only scopes the caller already holds, and the chain has a hop limit, so delegation only narrows permissions.

Subjects
Calling agents, identified as entities.
Resources and actions
Other agents and their skills: call, with the requested scopes, the caller’s scopes and the hop count as attributes.
Enforcement point
The calling agent before it sends a task, or the receiving agent before it accepts one. The application derives the caller’s scopes from the delegation it received.

Solution pattern · Self-hosted Speedle

Zero standing privileges (ZSP)

07 / Zero standing privileges

Just-in-time tokens support a zero standing privileges pattern

Under the right issuance and control conditions, just-in-time, short-lived, narrowly scoped credentials, combined with Speedle’s policy decisions and application-side enforcement, can support a zero standing privileges pattern. The example checks lifetime, not-before and token status; production also needs a trusted component that verifies the token, binds its claims to the subject, resource, action and task scope, and an atomic consume for single-use credentials.

Cross-cutting

Identity in. Decisions and explanations out

The same three concerns apply to every area in Build and Run.

Identity integration

Speedle decides; your IdP authenticates

Speedle is the authorization decision point. Authentication comes from your IdP or OAuth authorization server, for users and for agents; MCP authorization builds on OAuth. The application maps verified identities to principals (user, groups, entity), and Speedle decides on the principals it is given.

Audit & explainability

Every decision can be explained

Speedle’s diagnose API returns the decision, the reason, the effective roles and the policies examined, including which one matched and why. Applications log each decision with the agent and the delegating human. Diagnose exposes policy and request details, so keep it to trusted operators.

Risk mapping

Maps to OWASP LLM06:2025 Excessive Agency

The OWASP Top 10 for LLM Applications 2025 names Excessive Agency: an agent with more functionality, permission or autonomy than its task needs. Per-agent roles, per-tool checks, task- and time-bound delegation and human approval for high-risk actions narrow each of the three.

Where Speedle stops

Speedle does not detect prompt injection, filter model input or output, or verify model and dataset supply chains; use dedicated controls for those. It bounds what a compromised or misled agent can do: Speedle answers deny to any request outside policy, whatever the prompt said.

Integration approach

From agent intent to an enforced decision

An application asks for authorization before accessing data or executing a tool, then applies the returned decision.

  1. 01

    Describe identity and context

    Identify who initiated the request, which agent is acting, and the relevant user, role, and tenant.

    subject
  2. 02

    Map resource and action

    Map a tool, document, or business object to a resource, and the intended operation to an action.

    resource · action
  3. 03

    Request a policy decision

    Ask Speedle for a decision using readable, maintainable policies that describe the access rules.

    is-allowed
  4. 04

    Enforce it in the application

    Execute allowed operations, block denied ones, and record the application’s own execution result.

    allowed: true | false
