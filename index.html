Speedle policy modeler · Open source skill

Turn policy documents into reviewable SPDL

An Agent Skill for Claude Code that reads an employee handbook or regulation, asks about what the document leaves open, and models the result as RBAC + ABAC policies. It never guesses a rule.

What it produces5 files

From handbook clauses to tested policies

Every policy cites the clause it implements, or a confirmed answer. The model document includes a Mermaid role-inheritance diagram and each policy's rationale.

  • Importable .spdl for the file store, checked with spctl check.
  • ABAC conditions for department, location, data class and amount.
  • Executable cases covering allows, denies and approval boundaries.

Speedle MCP · Coming soon

Speedle MCP: one package, two deliberately separate modes

@speedle/mcp is planned as one npm package with a speedle-mcp binary that runs as a local stdio MCP server. It is not published on npm yet.

Follow the repository
Mode 01 · Launch previewcheck

Authorization checks

The planned check mode registers only is_allowed by default and reads only ADS configuration. diagnose, all_granted_roles and all_granted_permissions are opt-in through the --expose-diagnose, --expose-all-granted-roles and --expose-all-granted-permissions flags. diagnose works only with self-hosted Speedle; the server will not start with it against Speedle Cloud. It answers authorization questions; it does not enforce anything in the calling application.

  • Read-only authorization checks through the Speedle ADS REST API.
  • Subject, resource, action, and typed attributes as inputs.
  • ADS base URL, service name, and optional bearer token from environment variables.
Read the check-mode issue
Mode 02 · Launch previewmanage

Policy design and management

The planned manage mode registers only the management tools and reads only PMS configuration for designing and managing Speedle policies through the PMS REST API.

  • Services, authorization policies, and role policies.
  • SPDL validation and effective-policy explanation helpers.
  • A read-only option; destructive deletes require explicit target confirmation.
Read the manage-mode issue

Keep policy management out of the governed agent

Never give manage to an agent that is itself governed by these policies. An agent holding both check and management tools could be prompted into granting itself access.

Give a governed agent is_allowed only. That is the check default. diagnose, all_granted_roles and all_granted_permissions show policies, conditions and grants, so turn them on only in a check server for policy authors and operators, and never pass the --expose-* flags to the agent’s server.

There is no default mode that exposes both. Running with no mode is planned to print usage and exit non-zero.

02

Control what AI can access

Govern access while you build and run AI

Speedle’s policy engine applied wherever AI systems touch data, models, tools and other agents: in Build, before a model serves, and in Run, while it serves and acts. These are solution patterns, not shipped integrations with any ML or agent platform.

Concept

One decision point for building and running AI

Each area has an enforcement point in your application. It asks Speedle before it acts and enforces the answer.

Solution patterns

One policy pattern per area

One sentence and one representative rule per area. The full SPDL examples, with the attributes each check needs, are on the patterns page.

Build · 01 Data & training

Data and training

Training jobs read datasets and write checkpoints; consent and region are checked per dataset, and restricted data never enters training.

grant role training-pipeline read expr:^/datasets/ if consent == true && data_region == job_region

Build · 02 Model release

Model release

Registering, approving, promoting and rolling back are separate actions, and nobody approves a model they trained.

deny role release-manager approve expr:^/models/ if trained_by == request_user

Run · 03 Inference & RAG

Inference and RAG

The retriever asks about each document before its content enters the prompt, so the model only sees what the user may read.

grant role tenant-user retrieve expr:^/collections/ if doc_tenant == user_tenant && doc_label in user_clearances

Run · 04 Agents acting for users

Agents acting for users

The agent is checked within its delegation token’s scope, then the delegating user is checked with their current permissions.

grant entity triage-agent in-time if request_time < token_expires

Run · 05 Tool calls (MCP)

Tool calls over MCP

Every tool call is checked before it runs, and the arguments become attributes the policy can limit.

grant role billing-agent call /tools/issue-refund if amount <= 100 && customer_verified == true

Run · 06 Agent-to-agent (A2A)

Agent-to-agent calls

Each hop is checked, and the callee may receive only scopes the caller already holds.

grant role planner-agent call /agents/researcher if IsSubSet(requested_scopes, caller_scopes) && hops <= 2

Run · 07 Zero standing privileges · Self-hosted

Zero standing privileges

Just-in-time, short-lived tokens can support zero standing privileges when issuance and controls are in place.

grant role agent-runtime invoke /api/orders if expires_at > issued_at && expires_at - issued_at <= 600 && issued_at <= request_time + 60 && not_before <= request_time + 60 && request_time < expires_at && TokenUnused(token_id)

Cross-cutting

What every area has in common

Identity, audit, risk mapping and the boundary apply to every area in Build and Run.

Identity integration

Speedle decides; your IdP authenticates

Speedle is the authorization decision point. Authentication comes from your IdP or OAuth authorization server, for users and for agents; MCP authorization builds on OAuth. The application maps verified identities to principals (user, groups, entity) before it asks Speedle.

Audit & explainability

Diagnose and audit logs

Speedle’s diagnose API returns the decision, the reason, the effective roles and the policies examined, including which one matched and why. Applications log each decision with the agent and the delegating human. Diagnose exposes policy and request details, so keep it to trusted operators.

Risk mapping

Maps to OWASP LLM06:2025 Excessive Agency

The OWASP Top 10 for LLM Applications 2025 names Excessive Agency: an agent with more functionality, permission or autonomy than its task needs. Per-agent roles, per-tool checks, task- and time-bound delegation and human approval for high-risk actions narrow each of the three.

Boundary

Where Speedle stops

Speedle does not detect prompt injection, filter model input or output, or verify model and dataset supply chains; use dedicated controls for those. It bounds what a compromised or misled agent can do: Speedle answers deny to any request outside policy, whatever the prompt said.
