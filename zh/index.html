Speedle MCP预览

Speedle MCP：两种独立模式

未来，@speedle/mcp 将作为一个 npm 包发布，附带 speedle-mcp 命令，用于启动本地 stdio MCP 服务器。目前尚未发布。

关注开发进展
模式 01check

授权检查

规划中的 check 模式默认只注册 is_allowed，只读取 ADS 配置。diagnose、all_granted_roles 和 all_granted_permissions 需要分别用 --expose-diagnose、--expose-all-granted-roles 和 --expose-all-granted-permissions 参数显式开启。diagnose 只支持自托管 Speedle，连接 Speedle Cloud 时带上它服务不会启动。它只回答授权问题，不会在调用应用中执行访问控制。

  • 通过 Speedle ADS REST API 发起只读授权检查。
  • 输入：主体、资源、操作和带类型的属性。
  • 从环境变量读取 ADS 基础 URL、服务名和可选的 bearer 令牌。
查看 check 模式 issue
模式 02manage

策略设计与管理

规划中的 manage 模式只注册管理工具，只读取 PMS 配置，通过 PMS REST API 设计和管理 Speedle 策略。

  • 管理服务、授权策略和角色策略。
  • 提供 SPDL 校验和生效策略解释工具。
  • 支持只读选项；执行删除前必须明确确认目标。
查看 manage 模式 issue

别让受控智能体管理策略

不要给受这些策略约束的智能体开放 manage 模式。如果智能体同时拿到检查和管理工具，提示词可能诱导它给自己开通访问权限。

受控智能体只开放 is_allowed。这是 check 模式的默认设置。diagnose、all_granted_roles 和 all_granted_permissions 会展示策略、条件和授权，只在给策略编写者和运维人员使用的 check 服务中开启，不要给智能体的服务加 --expose-* 参数。

没有同时开放两类工具的默认模式。按规划，不指定模式时会打印用法，并以非零状态码退出。

02

面向 AI 的访问管理

AI 构建与运行，权限全程可控

从模型上线前的构建阶段，到模型服务与执行操作的运行阶段，Speedle 策略引擎都能管理 AI 系统对数据、模型、工具和其他智能体的访问。这里介绍的是解决方案模式，不是任何机器学习或智能体平台的已发布集成。

概念

AI 构建与运行，共用一个决策点

每个区域都在应用里设有策略执行点：操作前先问 Speedle，再按结果放行或拒绝。身份来自你的 IdP，决策和原因写入审计记录。

以下 SPDL 示例都用 Speedle 文件存储解析并评估过，覆盖允许和拒绝两种用例。名称、路径和属性仅作示例，实际由应用在请求决策时传入。策略执行点必须传入条件引用的所有属性。

构建

数据、训练、发布

01 / 数据与训练

哪些流水线能用哪些数据训练？

训练任务要读数据集、用算力、写检查点。每次读取数据集、启动任务或导出检查点前，应用都会先请求授权，并传入数据敏感度、租户、同意状态和区域等属性。

主体
训练流水线（实体）、机器学习工程师及其团队。
资源与操作
数据集：read。训练任务：start。检查点：export。
策略执行点
数据加载器打开数据集前、任务调度器分配算力前，以及制品库导出前。

02 / 模型发布

谁可以发布模型？

模型注册、审批、晋升和回滚分开授权，各由不同角色负责。职责分离后，训练模型的人不能审批同一个模型。

主体
机器学习工程师、发布经理和发布流水线的服务身份。
资源与操作
模型和端点：register、approve、promote、rollback。
策略执行点
模型注册表和发布流水线会在每次更改模型或端点状态前检查。

运行

AI 运行：检索与各类调用

03 / 推理与 RAG

提示词只放用户可读内容

用户、应用和租户都会调用模型。要实现权限感知的 RAG（检索增强生成），检索器会在内容进入提示词前，逐文档或逐集合向 Speedle 请求授权，让模型只看到请求用户有权阅读的内容。

  1. 1检索器查找候选文档。
  2. 2检索器带上用户的租户和许可级别，逐文档或逐集合向 Speedle 请求授权。
  3. 3获准内容才能进入提示词。
主体
发起请求的用户及其用户组；客户端应用和租户作为实体。
资源与操作
集合和文档：retrieve。模型：invoke。
策略执行点
检索器在文档进入提示词前检查；API 网关或推理服务在路由请求前检查。

04 / 智能体代用户操作

AI 智能体能代用户做什么？

智能体有自己的身份；用户的委托由签名的委托令牌证明，而不是靠请求里的声明。策略执行点先验证令牌，再向 Speedle 查询两次，两次都通过才放行：一次查智能体是否在令牌范围内，一次查委托用户此刻本人是否有这项权限。令牌签发后，用户一旦失去某项权限，智能体在下一次请求时也会随之失去。超过 100 的退款还需要一条由用户以外的人做出的审批记录。

  1. 1验证令牌：签名、签发方、有效期，以及令牌是否签发给这个智能体。
  2. 2智能体范围：以智能体为主体查询 Speedle，令牌范围作为属性传入。
  3. 3委托用户当下的权限：以令牌 sub 声明中的用户为主体查询 Speedle。
主体
范围检查以智能体（实体）为主体；第二次检查以委托用户为主体，用户取自已验证的令牌。
资源与操作
工单：read、update；订单：refund，金额作为属性传入。都仅限令牌范围内的操作和资源。
策略执行点
智能体运行时或应用后端在操作到达业务系统前检查。它负责验证令牌，只把验证过的声明传给 Speedle。
人工审批
策略执行点验证这笔退款的签名审批记录，并在第二次检查中把审批人作为 approved_by 传入。审批人不能是用户本人。
自托管选项
也可以只查一次，由自定义函数 DelegationValid 和 DelegatorAllowed 评估令牌和委托用户。Speedle Cloud 不支持自定义函数。

05 / 工具调用（MCP）

MCP 工具能这样调用吗？

每次调用工具，都要先检查再执行。工具是资源，调用是操作，参数则变成属性，退款金额上限等规则就能直接写进策略。

主体
每个智能体都有独立的实体身份和角色，权限可以按智能体、按工具分别控制。
资源与操作
工具：call，工具参数作为属性。
策略执行点
MCP 客户端宿主，或 MCP 服务器前的网关，在工具执行前检查。

06 / 智能体间调用（A2A）

A2A 授权：谁能调用谁？

委托链每一跳都要检查。接收方只能拿到调用方已有的权限范围，跳数也有上限，因此每次委托都只会收窄权限。

主体
调用方智能体，以实体标识。
资源与操作
其他智能体及其技能：call。属性包括请求权限范围、调用方权限范围和跳数。
策略执行点
调用方发送任务前，或接收方接受任务前，由对应的智能体检查。应用根据收到的委托确定调用方的权限范围。

零常驻权限（ZSP）

07 / 零常驻权限

即时令牌支撑零常驻权限模式

签发和管控到位时，即时签发、短期有效、范围受限的授权凭证，结合 Speedle 的策略决策和应用侧执行控制，可以构建零常驻权限模式。示例检查有效期、生效时间和令牌状态；生产环境还需要可信组件验证令牌，把声明绑定到主体、资源、操作和任务范围，并原子消费单次使用的凭证。

贯穿全流程

输入身份信息，输出决策与解释

这三件事贯穿构建和运行的每个区域。

身份集成

Speedle 管授权，IdP 管认证

Speedle 是授权决策点，用户和智能体则由你的 IdP 或 OAuth 授权服务器认证，MCP 授权基于 OAuth。应用把验证过的身份映射为主体（用户、用户组、实体），Speedle 根据这些主体作出决策。

审计与可解释性

每项决策都说得清

Speedle 的诊断 API 返回决策、原因、生效角色和检查过的策略，说清匹配了哪条策略、为什么。应用记录每项决策、相关智能体和发起委托的用户。诊断接口会暴露策略和请求详情，只向可信运维人员开放。

风险映射

对应 OWASP LLM06:2025 过度代理

OWASP 2025 年大模型应用十大风险提到的过度代理，是指智能体的功能、权限或自主性超出任务需要。按智能体划分角色、按工具检查、让委托绑定任务和时限，再对高风险操作做人工审批，可以分别收敛这三类风险。

Speedle 的能力边界

Speedle 不检测提示词注入，不过滤模型输入或输出，也不验证模型和数据集供应链，这些需要专门的控制措施。它能限制遭攻陷或受误导的智能体做什么：无论提示词怎么写，只要请求不符合策略，Speedle 就拒绝。

集成方式

从智能体意图到应用执行决策

应用访问数据或调用工具前先请求授权，再按返回结果放行或拦截。

  1. 01

    明确身份和上下文

    说明谁发起请求、哪个智能体在执行，以及相关的用户、角色和租户。

    subject
  2. 02

    映射资源和操作

    把工具、文档或业务对象映射为资源，把要执行的操作映射为动作。

    resource · action
  3. 03

    向 Speedle 请求决策

    用清晰、可维护的策略写清访问规则，再向 Speedle 请求决策。

    is-allowed
  4. 04

    在应用中执行决策

    放行允许的操作，拦截拒绝的操作，并记录应用自己的执行结果。

    allowed: true | false
