Speedle MCP预览

Speedle MCP：两种独立模式

@speedle/mcp 已在 npm 发布。它是一个 npm 包，附带 speedle-mcp 命令，用于在本地以 stdio 方式运行 MCP 服务器。

阅读 README
模式 01check

授权检查

check 模式默认只注册 is_allowed，只读取 ADS 配置。diagnose、all_granted_roles 和 all_granted_permissions 需要分别用 --expose-diagnose、--expose-all-granted-roles 和 --expose-all-granted-permissions 参数显式开启。diagnose 只支持自托管 Speedle，连接 Speedle Cloud 时带上它服务不会启动。它只回答授权问题，不会在调用应用中执行访问控制。

  • 通过 Speedle ADS REST API 发起只读授权检查。
  • 输入：主体、资源、操作和带类型的属性。
  • 从环境变量读取 ADS 基础 URL、服务名和可选的 bearer 令牌。
查看 check 模式配置
模式 02manage

策略设计与管理

manage 模式只注册管理工具，只读取 PMS 配置，通过 PMS REST API 设计和管理 Speedle 策略。

  • 管理服务、授权策略和角色策略。
  • 以 SPDL 展示生效策略；策略在创建时由 PMS 校验。
  • 支持只读选项；执行删除前必须明确确认目标。
查看 manage 模式配置

别让受控智能体管理策略

不要给受这些策略约束的智能体开放 manage 模式。如果智能体同时拿到检查和管理工具，提示词可能诱导它给自己开通访问权限。

受控智能体只开放 is_allowed。这是 check 模式的默认设置。diagnose、all_granted_roles 和 all_granted_permissions 会展示策略、条件和授权，只在给策略编写者和运维人员使用的 check 服务中开启，不要给智能体的服务加 --expose-* 参数。

没有同时开放两类工具的默认模式。不带模式运行 speedle-mcp 会打印用法，并以非零状态码退出。

需要 Node.js 22 或更高版本。这些示例与已发布的包 README 一致。上面的 Claude Code 插件固定使用 @speedle/mcp@0.2.1 版本。

02

用策略约束 AI

AI 构建与运行，权限全程可控

从模型上线前的构建阶段，到模型服务与执行操作的运行阶段，Speedle 策略引擎都能管理 AI 系统对数据、模型、工具和其他智能体的访问。这里介绍的是解决方案模式，不是任何机器学习或智能体平台的已发布集成。

概念

AI 构建与运行，共用一个决策点

每个区域都在应用里设有策略执行点：操作前先问 Speedle，再按结果放行或拒绝。

解决方案模式

每个区域一条策略模式

每个区域一句话、一条代表性规则。完整 SPDL 示例和每次检查需要的属性，都在模式页面。

构建 · 01 数据与训练

数据与训练

训练任务读取数据集并写入检查点；同意状态和区域逐数据集检查，受限数据不会进入训练。

grant role training-pipeline read expr:^/datasets/ if consent == true && data_region == job_region

构建 · 02 模型发布

模型发布

模型注册、审批、晋升和回滚是分开的操作，训练模型的人不能审批同一个模型。

deny role release-manager approve expr:^/models/ if trained_by == request_user

运行 · 03 推理与 RAG

推理与 RAG

检索器在文档内容进入提示词前逐篇请求授权，模型只看到用户有权阅读的内容。

grant role tenant-user retrieve expr:^/collections/ if doc_tenant == user_tenant && doc_label in user_clearances

运行 · 04 智能体代用户操作

智能体代用户操作

先检查智能体是否在委托令牌的范围内，再检查委托用户此刻本人的权限。

grant entity triage-agent in-time if request_time < token_expires

运行 · 05 工具调用（MCP）

MCP 工具调用

每次工具调用都在执行前检查，参数作为属性，交给策略限制。

grant role billing-agent call /tools/issue-refund if amount <= 100 && customer_verified == true

运行 · 06 智能体间调用（A2A）

智能体间调用

委托链每一跳都要检查，接收方只能拿到调用方已有的权限范围。

grant role planner-agent call /agents/researcher if IsSubSet(requested_scopes, caller_scopes) && hops <= 2

运行 · 07 零常驻权限 · 自托管

零常驻权限

签发和管控到位时，即时签发、短期有效的令牌可以支撑零常驻权限模式。在 Speedle 里，你可以把零常驻权限策略写成 SPDL 策略，并在每次请求时强制执行：权限只在你设定的时间窗口和条件内存在。

grant role agent-runtime invoke /api/orders if expires_at > issued_at && expires_at - issued_at <= 600 && issued_at <= request_time + 60 && not_before <= request_time + 60 && request_time < expires_at && TokenUnused(token_id)

贯穿全流程

每个区域共有的四件事

身份、审计、风险映射和能力边界贯穿构建和运行的每个区域。

身份集成

Speedle 管授权，IdP 管认证

Speedle 是授权决策点，用户和智能体则由你的 IdP 或 OAuth 授权服务器认证，MCP 授权基于 OAuth。应用先把验证过的身份映射为主体（用户、用户组、实体），再向 Speedle 请求决策。

审计与可解释性

诊断与审计日志

Speedle 的诊断 API 返回决策、原因、生效角色和检查过的策略，说清匹配了哪条策略、为什么。应用记录每项决策、相关智能体和发起委托的用户。诊断接口会暴露策略和请求详情，只向可信运维人员开放。

风险映射

对应 OWASP LLM06:2025 过度代理

OWASP 2025 年大模型应用十大风险提到的过度代理，是指智能体的功能、权限或自主性超出任务需要。按智能体划分角色、按工具检查、让委托绑定任务和时限，再对高风险操作做人工审批，可以分别收敛这三类风险。

边界

Speedle 的能力边界

Speedle 不检测提示词注入，不过滤模型输入或输出，也不验证模型和数据集供应链，这些需要专门的控制措施。它能限制遭攻陷或受误导的智能体做什么：无论提示词怎么写，只要请求不符合策略，Speedle 就拒绝。
