Speedle MCPプレビュー

Speedle MCP：1つのパッケージ、明確に分離された2つのモード

@speedle/mcp は npm で公開されています。ローカルの stdio MCP サーバーとして動作する speedle-mcp バイナリを含む 1 つのパッケージです。

README を読む
モード 01check

認可チェック

check モードはデフォルトで is_allowed のみを登録し、ADS 設定のみを読み込みます。diagnose、all_granted_roles、all_granted_permissions は、--expose-diagnose、--expose-all-granted-roles、--expose-all-granted-permissions フラグによってオプトインできます。diagnose はセルフホストの Speedle でのみ動作します。サーバーは Speedle Cloud に対しては起動しません。認可に関する質問に回答するのみで、呼び出し側アプリケーションで何かを強制することはありません。

  • Speedle ADS REST API を介した読み取り専用の認可チェック。
  • 主体、リソース、アクション、型付き属性を入力として受け取ります。
  • 環境変数から ADS ベース URL、サービス名、オプションのベアラートークンを取得します。
check モードの設定を読む
モード 02manage

ポリシーの設計と管理

manage モードは管理ツールのみを登録し、PMS REST API を介して Speedle ポリシーを設計および管理するための PMS 設定のみを読み込みます。

  • サービス、認可ポリシー、ロールポリシー。
  • SPDL 形式の有効なポリシー。PMS は作成時に各ポリシーを検証します。
  • 読み取り専用オプション。破壊的な削除には明示的なターゲットの確認が必要です。
manage モードの設定を読む

管理対象のエージェントにポリシー管理権限を与えないでください

これらのポリシーによって管理されるエージェント自身に manage を与えないでください。チェックツールと管理ツールの両方を保持するエージェントは、プロンプトによって自身にアクセス権を付与してしまう可能性があります。

管理対象のエージェントには is_allowed のみを与えてください。それが check のデフォルトです。diagnose、all_granted_roles、all_granted_permissions はポリシー、条件、付与内容を表示するため、ポリシー作成者や運用者向けのチェックサーバーでのみ有効にし、エージェントのサーバーに --expose-* フラグを渡さないでください。

両方を公開するデフォルトモードはありません。モードを指定せずに speedle-mcp を実行すると、使用法が出力され、非ゼロで終了します。

Node.js 22 以降が必要です。これらの例は公開されているパッケージの README と一致しています。上記の Claude Code プラグインは @speedle/mcp@0.2.1 に固定されています。

AI リスク検知

計画中

AI はより多くの次元や関係性を横断して、単一のルールでは見落とされがちなリスクを発見できます。これは Speedle が探究および構築している方向性であり、既存のリリース機能ではありません。ポリシーが拒否権を保持します：リスクシグナルによって監視や保護を強化することはできますが、拒否を許可に変更することはありません。

02

Control what AI can access

AI の構築と運用におけるアクセスを統制

AI システムがデータ、モデル、ツール、他のエージェントと接するあらゆる場所に適用される Speedle のポリシーエンジン：モデル提供前の構築フェーズ、および提供・動作中の運用フェーズ。これらはソリューションパターンであり、特定の ML やエージェントプラットフォームとの既成連携機能ではありません。

コンセプト

AI の構築と運用のための単一の決定ポイント

各領域にはアプリケーション内の執行ポイントがあります。動作を実行する前に Speedle に問い合わせ、その回答を執行します。

ソリューションパターン

領域ごとに1つのポリシーパターン

領域ごとに1つの文と1つの代表的なルール。各チェックに必要な属性を含む完全な SPDL 例は、パターンページにあります。

ビルド · 01 データとトレーニング

データとトレーニング

トレーニングジョブはデータセットを読み取り、チェックポイントを書き込みます。同意とリージョンはデータセットごとにチェックされ、制限されたデータがトレーニングに入ることはありません。

grant role training-pipeline read expr:^/datasets/ if consent == true && data_region == job_region

ビルド · 02 モデルリリース

モデルリリース

登録、承認、昇格、ロールバックは個別の操作であり、自分がトレーニングしたモデルを承認することはできません。

deny role release-manager approve expr:^/models/ if trained_by == request_user

実行 · 03 推論と RAG

推論と RAG

リトリーバーはドキュメントの内容がプロンプトに入る前に各ドキュメントについて問い合わせるため、モデルにはユーザーが閲覧を許可されたもののみが表示されます。

grant role tenant-user retrieve expr:^/collections/ if doc_tenant == user_tenant && doc_label in user_clearances

実行 · 04 ユーザーに代わって動作するエージェント

ユーザーに代わって動作するエージェント

エージェントは委任トークンのスコープ内でチェックされ、その後委任ユーザーが現在の権限でチェックされます。

grant entity triage-agent in-time if request_time < token_expires

実行 · 05 ツール呼び出し (MCP)

MCP によるツール呼び出し

すべてのツール呼び出しは実行前にチェックされ、引数はポリシーが制限できる属性になります。

grant role billing-agent call /tools/issue-refund if amount <= 100 && customer_verified == true

実行 · 06 エージェント間呼び出し (A2A)

エージェント間呼び出し

各ホップがチェックされ、呼び出し先は呼び出し元がすでに保持しているスコープのみを受け取ることができます。

grant role planner-agent call /agents/researcher if IsSubSet(requested_scopes, caller_scopes) && hops <= 2

実行 · 07 常設特権ゼロ · セルフホスト

常設特権ゼロ (ZSP)

適切な発行と制御が行われている場合、ジャストインタイムで有効期間の短いトークンにより常設特権ゼロのパターンを実現できます。Speedle では ZSP 戦略をポリシーとして定義し、すべてのリクエストで適用できます：SPDL で記述した時間枠と条件内でのみアクセスが存在します。

grant role agent-runtime invoke /api/orders if expires_at > issued_at && expires_at - issued_at <= 600 && issued_at <= request_time + 60 && not_before <= request_time + 60 && request_time < expires_at && TokenUnused(token_id)

横断的関心事

すべての領域に共通する要素

アイデンティティ、監査、リスクマッピング、境界は、構築と運用のすべての領域に適用されます。

アイデンティティ統合

Speedle が認可を決定し、IdP が認証を行う

Speedle は認可決定ポイントです。認証は IdP または OAuth 認可サーバーから行われ、ユーザーとエージェントの両方に適用されます。MCP 認可は OAuth 上に構築されます。アプリケーションは検証されたアイデンティティをプリンシパル（ユーザー、グループ、エンティティ）にマッピングしてから Speedle に問い合わせます。

監査と説明可能性

診断および監査ログ

Speedle の diagnose API は決定、理由、有効なロール、およびどのポリシーがなぜ一致したかを含む検証されたポリシーを返します。アプリケーションはエージェントおよび委任した人間とともに各決定をログに記録します。診断はポリシーとリクエストの詳細を公開するため、信頼できる運用者に限定してください。

リスクマッピング

OWASP LLM06:2025 過剰なエージェンシーに対応

OWASP Top 10 for LLM Applications 2025 では過剰なエージェンシー（Excessive Agency）を挙げています：タスクが必要とする以上の機能、権限、または自律性を持つエージェントです。エージェントごとのロール、ツールごとのチェック、タスクと時間にバインドされた委任、および高リスクのアクションに対する人間の承認により、この3つをそれぞれ絞り込みます。

境界

Speedle の適用範囲

Speedle はプロンプトインジェクションの検出、モデルの入出力フィルタリング、モデルやデータセットのサプライチェーン検証は行いません。これらには専用の管理策を使用してください。侵害された、または誤導されたエージェントができることを制限します：プロンプトの内容に関わらず、ポリシー外のすべてのリクエストに対して Speedle は拒否を返します。
