Speedle MCPVista previa

Speedle MCP: un paquete, dos modos deliberadamente separados

@speedle/mcp está publicado en npm. Es un paquete con un binario speedle-mcp que se ejecuta como un servidor MCP stdio local.

Leer el README
Modo 01check

Comprobaciones de autorización

El modo check registra solo is_allowed de forma predeterminada y solo lee la configuración de ADS. diagnose, all_granted_roles y all_granted_permissions son opcionales mediante los indicadores --expose-diagnose, --expose-all-granted-roles y --expose-all-granted-permissions. diagnose funciona solo con Speedle autohospedado; el servidor no se iniciará con él en Speedle Cloud. Responde preguntas de autorización; no aplica nada en la aplicación que realiza la llamada.

  • Comprobaciones de autorización de solo lectura a través de la API REST de Speedle ADS.
  • Sujeto, recurso, acción y atributos tipados como entradas.
  • URL base de ADS, nombre de servicio y token de portador opcional desde variables de entorno.
Leer la configuración del modo check
Modo 02manage

Diseño y gestión de políticas

El modo manage registra solo las herramientas de gestión y solo lee la configuración de PMS para diseñar y gestionar políticas de Speedle a través de la API REST de PMS.

  • Servicios, políticas de autorización y políticas de roles.
  • Políticas vigentes como SPDL; PMS valida cada política al crearla.
  • Una opción de solo lectura; las eliminaciones destructivas requieren confirmación explícita del objetivo.
Leer la configuración del modo manage

Mantenga la gestión de políticas fuera del agente gobernado

Nunca otorgue el modo manage a un agente que esté gobernado por estas políticas. Un agente que posea herramientas de comprobación y de gestión podría ser inducido mediante prompts a otorgarse acceso a sí mismo.

Proporcione al agente gobernado únicamente is_allowed. Ese es el valor predeterminado de check. diagnose, all_granted_roles y all_granted_permissions muestran políticas, condiciones y concesiones, por lo que debe activarlos solo en un servidor de verificación para autores y operadores de políticas, y nunca pasar los indicadores --expose-* al servidor del agente.

No existe un modo predeterminado que exponga ambos. Ejecutar speedle-mcp sin ningún modo muestra el uso y sale con un código distinto de cero.

Requiere Node.js 22 o posterior. Estos ejemplos coinciden con el README del paquete publicado. El complemento de Claude Code anterior fija @speedle/mcp@0.2.1.

Detección de riesgos de IA

Planificado

La IA puede analizar más dimensiones y relaciones para encontrar riesgos que una sola regla no detecta. Esta es una dirección que Speedle está explorando y desarrollando, no una característica definitiva. La política mantiene el veto: una señal de riesgo puede añadir supervisión o protección, pero nunca convierte una denegación en una autorización.

02

Control what AI can access

Gobierne el acceso mientras construye y ejecuta IA

El motor de políticas de Speedle aplicado dondequiera que los sistemas de IA interactúan con datos, modelos, herramientas y otros agentes: en la fase de construcción, antes de que el modelo esté en servicio, y en la fase de ejecución, mientras sirve y actúa. Estos son patrones de solución, no integraciones predeterminadas con ninguna plataforma de ML o agentes.

Concepto

Un único punto de decisión para construir y ejecutar IA

Cada área tiene un punto de aplicación en su aplicación. Consulta a Speedle antes de actuar y aplica la respuesta.

Patrones de solución

Un patrón de políticas por área

Una frase y una regla representativa por área. Los ejemplos completos de SPDL, con los atributos que necesita cada comprobación, están en la página de patrones.

Construcción · 01 Datos y entrenamiento

Datos y entrenamiento

Los trabajos de entrenamiento leen conjuntos de datos y escriben puntos de control; el consentimiento y la región se verifican por conjunto de datos, y los datos restringidos nunca entran al entrenamiento.

grant role training-pipeline read expr:^/datasets/ if consent == true && data_region == job_region

Construcción · 02 Publicación de modelos

Publicación de modelos

Registrar, aprobar, promocionar y revertir son acciones independientes, y nadie aprueba un modelo que haya entrenado.

deny role release-manager approve expr:^/models/ if trained_by == request_user

Ejecución · 03 Inferencia y RAG

Inferencia y RAG

El recuperador consulta sobre cada documento antes de que su contenido ingrese al prompt, de modo que el modelo solo ve lo que el usuario tiene permiso para leer.

grant role tenant-user retrieve expr:^/collections/ if doc_tenant == user_tenant && doc_label in user_clearances

Ejecución · 04 Agentes actuando en nombre de usuarios

Agentes actuando en nombre de usuarios

El agente se verifica dentro del alcance de su token de delegación, luego se verifica el usuario delegador con sus permisos actuales.

grant entity triage-agent in-time if request_time < token_expires

Ejecución · 05 Llamadas a herramientas (MCP)

Llamadas a herramientas mediante MCP

Cada llamada a una herramienta se comprueba antes de ejecutarse, y los argumentos se convierten en atributos que la política puede limitar.

grant role billing-agent call /tools/issue-refund if amount <= 100 && customer_verified == true

Ejecución · 06 Llamadas entre agentes (A2A)

Llamadas de agente a agente

Se verifica cada salto, y el receptor solo puede recibir los alcances que el emisor ya posee.

grant role planner-agent call /agents/researcher if IsSubSet(requested_scopes, caller_scopes) && hops <= 2

Ejecución · 07 Privilegios permanentes cero · Autohospedado

Privilegios permanentes cero (ZSP)

Los tokens de corta duración emitidos justo a tiempo pueden admitir privilegios permanentes cero cuando la emisión y los controles están implementados. Speedle es donde define su estrategia ZSP como política y la aplica en cada solicitud: el acceso existe solo dentro del período de tiempo y las condiciones escritas en SPDL.

grant role agent-runtime invoke /api/orders if expires_at > issued_at && expires_at - issued_at <= 600 && issued_at <= request_time + 60 && not_before <= request_time + 60 && request_time < expires_at && TokenUnused(token_id)

Aspectos transversales

Lo que todas las áreas tienen en común

Identidad, auditoría, mapeo de riesgos y límites se aplican a todas las áreas de construcción y ejecución.

Integración de identidad

Speedle decide; su IdP autentica

Speedle es el punto de decisión de autorización. La autenticación proviene de su IdP o servidor de autorización OAuth, tanto para usuarios como para agentes; la autorización MCP se basa en OAuth. La aplicación asigna identidades verificadas a entidades principales (usuario, grupos, entidad) antes de consultar a Speedle.

Auditoría y explicabilidad

Diagnóstico y registros de auditoría

La API diagnose de Speedle devuelve la decisión, el motivo, los roles efectivos y las políticas examinadas, incluido cuál coincidió y por qué. Las aplicaciones registran cada decisión con el agente y el humano delegador. Diagnose expone detalles de políticas y solicitudes, por lo que debe limitarse a operadores de confianza.

Mapeo de riesgos

Se asigna a OWASP LLM06:2025 Exceso de agencia

El documento OWASP Top 10 for LLM Applications 2025 identifica el Exceso de agencia: un agente con más funcionalidad, permisos o autonomía de los que requiere su tarea. Los roles por agente, las comprobaciones por herramienta, la delegación limitada por tarea y tiempo, y la aprobación humana para acciones de alto riesgo acotan cada uno de estos tres factores.

Límite

Dónde se detiene Speedle

Speedle no detecta la inyección de prompts, no filtra entradas o salidas de modelos ni verifica las cadenas de suministro de modelos y conjuntos de datos; utilice controles dedicados para ello. Limita lo que puede hacer un agente comprometido o engañado: Speedle responde con denegación a cualquier solicitud fuera de la política, sin importar lo que indique el prompt.
