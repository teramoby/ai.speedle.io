Speedle 정책 모델러 · 오픈 소스 에이전트 스킬사용 가능

정책 문서를 검토 가능한 SPDL로 변환

직원 핸드북이나 규정을 읽고 명확하지 않은 부분에 대해 질문한 후 그 결과를 RBAC + ABAC 정책으로 모델링하는 에이전트 스킬입니다. 결코 규칙을 추측하지 않습니다.

생성물5개 파일

핸드북 조항에서 검증된 정책까지

모든 정책은 구현하는 조항이나 확인된 답변을 명시합니다. 모델 문서에는 Mermaid 역할 상속 다이어그램과 각 정책의 근거가 포함됩니다.

  • spctl check로 검증되어 파일 저장소로 직접 가져올 수 있는 .spdl.
  • 부서, 위치, 데이터 등급 및 금액에 대한 ABAC 조건.
  • 허용, 거부 및 승인 경계를 포괄하는 실행 가능한 케이스.

Speedle MCP프리뷰

Speedle MCP: 단일 패키지, 의도적으로 분리된 두 가지 모드

@speedle/mcp는 npm에 배포되어 있습니다. 로컬 stdio MCP 서버로 실행되는 speedle-mcp 바이너리가 포함된 단일 패키지입니다.

README 읽기
모드 01check

인가 확인

check 모드는 기본적으로 is_allowed만 등록하고 ADS 구성만 읽습니다. diagnose, all_granted_roles, all_granted_permissions는 --expose-diagnose, --expose-all-granted-roles, --expose-all-granted-permissions 플래그를 통해 선택적으로 활성화됩니다. diagnose는 자체 호스팅 Speedle에서만 작동하며 Speedle Cloud를 대상으로는 서버가 시작되지 않습니다. 인가 관련 질의에 응답할 뿐 호출 애플리케이션에서 직접 정책을 강제하지는 않습니다.

  • Speedle ADS REST API를 통한 읽기 전용 인가 확인.
  • 주체, 리소스, 작업 및 형식화된 속성을 입력으로 받습니다.
  • 환경 변수를 통한 ADS 기본 URL, 서비스 이름 및 선택적 베어러 토큰 제공.
check 모드 설정 읽기
모드 02manage

정책 설계 및 관리

manage 모드는 관리 도구만 등록하며 PMS REST API를 통해 Speedle 정책을 설계하고 관리하기 위한 PMS 구성만 읽습니다.

  • 서비스, 인가 정책 및 역할 정책.
  • SPDL 형식의 유효 정책. PMS는 생성 시 각 정책을 검증합니다.
  • 읽기 전용 옵션 제공. 파괴적 삭제에는 명시적인 대상 확인이 필요합니다.
manage 모드 설정 읽기

관리 대상 에이전트에 정책 관리 도구를 제공하지 마세요

이러한 정책의 거버넌스를 받는 에이전트 자체에는 절대 manage 도구를 부여하지 마세요. 확인 도구와 관리 도구를 모두 보유한 에이전트는 프롬프트에 의해 스스로에게 접근 권한을 부여하도록 유도될 수 있습니다.

관리 대상 에이전트에는 is_allowed만 제공하세요. 이것이 check 모드의 기본값입니다. diagnose, all_granted_roles, all_granted_permissions는 정책, 조건 및 부여된 권한을 표시하므로 정책 작성자 및 운영자를 위한 확인 서버에서만 활성화하고 에이전트 서버에는 절대 --expose-* 플래그를 전달하지 마세요.

두 가지를 모두 노출하는 기본 모드는 없습니다. 모드 없이 speedle-mcp를 실행하면 사용법이 출력되고 0이 아닌 값으로 종료됩니다.

Node.js 22 이상이 필요합니다. 이 예제들은 공개된 패키지 README와 일치합니다. 위의 Claude Code 플러그인은 @speedle/mcp@0.2.1로 고정되어 있습니다.

AI 위험 탐지

계획됨

AI는 단일 규칙에서 파악하지 못하는 위험을 찾기 위해 더 많은 차원과 관계를 살펴볼 수 있습니다. 이는 Speedle이 탐색하고 구축 중인 방향이며 정식 출시된 기능이 아닙니다. 정책이 거부권을 유지합니다: 위험 신호는 조사나 보호를 강화할 수 있지만 거부를 허용으로 변경하지는 않습니다.

AI 구축 및 실행 시 접근 거버넌스

AI 시스템이 데이터, 모델, 도구 및 다른 에이전트와 접하는 모든 위치에 적용되는 Speedle의 정책 엔진: 모델 제공 전의 빌드 단계와 제공 및 동작 중인 실행 단계. 이는 솔루션 패턴이며 특정 ML 또는 에이전트 플랫폼과의 완성형 연동 기능이 아닙니다.

개념

AI 구축 및 실행을 위한 단일 결정 포인트

각 영역에는 애플리케이션 내의 집행 포인트가 있습니다. 동작하기 전에 Speedle에 확인하고 그 결정을 집행합니다.

솔루션 패턴

영역별 단일 정책 패턴

영역별 한 문장과 하나의 대표 규칙. 각 확인에 필요한 속성을 포함한 전체 SPDL 예제는 패턴 페이지에 있습니다.

빌드 · 01 데이터 및 훈련

데이터 및 훈련

훈련 작업은 데이터셋을 읽고 체크포인트를 작성합니다. 동의 및 리전은 데이터셋별로 확인되며 제한된 데이터는 훈련에 절대 포함되지 않습니다.

grant role training-pipeline read expr:^/datasets/ if consent == true && data_region == job_region

빌드 · 02 모델 배포

모델 배포

등록, 승인, 승격 및 롤백은 별도의 작업이며, 자신이 훈련한 모델을 직접 승인할 수 없습니다.

deny role release-manager approve expr:^/models/ if trained_by == request_user

실행 · 03 추론 및 RAG

추론 및 RAG

리트리버는 문서 내용이 프롬프트에 들어가기 전에 각 문서에 대해 확인하므로 모델은 사용자가 읽을 수 있는 권한이 있는 내용만 보게 됩니다.

grant role tenant-user retrieve expr:^/collections/ if doc_tenant == user_tenant && doc_label in user_clearances

실행 · 04 사용자를 대신하는 에이전트

사용자를 대신하는 에이전트

에이전트는 위임 토큰 범위 내에서 확인된 후 위임 사용자의 현재 권한으로 확인됩니다.

grant entity triage-agent in-time if request_time < token_expires

실행 · 05 도구 호출(MCP)

MCP를 통한 도구 호출

모든 도구 호출은 실행 전에 확인되며, 인수는 정책이 제한할 수 있는 속성이 됩니다.

grant role billing-agent call /tools/issue-refund if amount <= 100 && customer_verified == true

실행 · 06 에이전트 간 호출(A2A)

에이전트 간 호출

각 홉이 확인되며, 호출 수신자는 호출자가 이미 보유한 범위만 받을 수 있습니다.

grant role planner-agent call /agents/researcher if IsSubSet(requested_scopes, caller_scopes) && hops <= 2

실행 · 07 상시 권한 배제 · 자체 호스팅

상시 권한 배제(ZSP)

적절한 발급 및 통제가 이루어질 때, 즉시 발급되는 수명이 짧은 토큰은 상시 권한 배제 패턴을 지원할 수 있습니다. Speedle은 ZSP 전략을 정책으로 정의하고 모든 요청에 집행하는 공간입니다: SPDL에 작성된 시간 범위와 조건 내에서만 접근이 유효합니다.

grant role agent-runtime invoke /api/orders if expires_at > issued_at && expires_at - issued_at <= 600 && issued_at <= request_time + 60 && not_before <= request_time + 60 && request_time < expires_at && TokenUnused(token_id)

공통 관심사

모든 영역의 공통점

신원, 감사, 위험 매핑 및 경계는 빌드 및 실행의 모든 영역에 적용됩니다.

신원 통합

Speedle이 인가를 결정하고 IdP가 인증을 수행합니다

Speedle은 인가 결정 포인트입니다. 인증은 사용자와 에이전트 모두를 위해 IdP 또는 OAuth 인가 서버에서 제공되며, MCP 인가는 OAuth를 기반으로 구축됩니다. 애플리케이션은 검증된 신원을 주체(사용자, 그룹, 엔티티)에 매핑한 후 Speedle에 요청합니다.

감사 및 설명 가능성

진단 및 감사 로그

Speedle의 진단 API는 결정, 이유, 유효한 역할 및 일치한 정책과 이유를 포함하여 검사된 정책을 반환합니다. 애플리케이션은 에이전트 및 위임한 사용자와 함께 각 결정을 기록합니다. 진단은 정책 및 요청 세부 정보를 노출하므로 신뢰할 수 있는 운영자에게만 제한해야 합니다.

위험 매핑

OWASP LLM06:2025 과도한 에이전시 매핑

OWASP LLM 애플리케이션 10대 위험 2025에서는 과도한 에이전시(Excessive Agency)를 지목합니다: 작업에 필요한 것보다 더 많은 기능, 권한 또는 자율성을 가진 에이전트입니다. 에이전트별 역할, 도구별 확인, 작업 및 시간에 한정된 위임, 고위험 작업에 대한 사람의 승인을 통해 이 세 가지를 각각 좁힐 수 있습니다.

경계

Speedle의 경계

Speedle은 프롬프트 주입을 탐지하거나 모델 입력 및 출력을 필터링하거나 모델 및 데이터셋 공급망을 검증하지 않습니다. 이러한 작업에는 전용 제어 장치를 사용하세요. 손상되었거나 잘못 유도된 에이전트가 수행할 수 있는 작업을 제한합니다: 프롬프트 내용에 관계없이 정책 범위를 벗어난 모든 요청에 대해 Speedle은 거부를 반환합니다.
